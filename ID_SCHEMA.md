# ID Schema Explanation

This document explains how IDs are computed and transformed through the evaluation pipeline.

## Overview

IDs flow through three stages:
1. **Input Solutions** (`model_solutions.jsonl`)
2. **Raw Evaluator Output** (`evaluator_raw.jsonl`)
3. **Parsed Evaluator Gradings** (`*.eval.jsonl`)

## Stage 1: Input Solutions

**File:** `data/test_data/model_solutions.jsonl`

```json
{
  "problem_id": "APMO-2025-1",
  "generator": "gpt-5",
  "solution": "...",
  "problem": "...",
  "model": "gpt-5",
  ...
}
```

**Key fields:**
- `problem_id`: Unique problem identifier (e.g., "APMO-2025-1")
- `generator` or `model`: Model that generated the solution

## Stage 2: Raw Evaluator Output

**File:** `data/test_data/evaluation_outputs/evaluation_runs/.../evaluator_raw.jsonl`

```json
{
  "id": 0,
  "problem": "...",
  "metadata": {
    "problem_id": "APMO-2025-1",
    "generator": "gpt-5",
    "solution": "...",
    "model": "gpt-5",
    ...
  },
  "response": "<score>7</score><assessment>...</assessment>",
  "generation_info": {...}
}
```

**How IDs are computed:**
- `id`: **Sequential index** (0, 1, 2, ...) - just the position in the dataset
  - Generated by `main.py` when loading the dataset
  - Not the actual problem ID!
- `metadata.problem_id`: **Preserved** from input - the actual problem ID
- `metadata.generator`: **Preserved** from input - the solution generator model

**Why `id` is just an index:**
- The evaluator (`main.py`) treats the solutions dataset as a generic list
- It assigns sequential IDs automatically (0, 1, 2, ...)
- All original data is preserved in the `metadata` field

## Stage 3: Parsed Evaluator Gradings

**File:** `data/test_data/evaluation_outputs/evaluator_gradings/.../gemini-2.5-pro.eval.jsonl`

```json
{
  "id": "APMO-2025-1",
  "score": 7.0,
  "unique_id": "APMO-2025-1::gpt-5",
  "generator": "gpt-5",
  "assessment": "...",
  "errors": "..."
}
```

**Note:** The `generator` field uses the **sanitized model name** (e.g., `"qwen3-235b"` not `"openrouter/qwen/qwen3-235b"`) to match with `expert_gradings.jsonl`.

**How IDs are computed** (from `write_per_generator_eval`):

### Step 1: Extract problem ID from raw output
```python
pid = r.get('id')  # Gets the sequential index (0, 1, 2, ...)
meta = r.get('metadata')
# Try to find actual problem_id in metadata
problem_id = meta.get('problem_id')  # "APMO-2025-1"
```

### Step 2: Find the generator model
The function tries multiple strategies to find which model generated this solution:

1. **metadata.model** - Most common
2. **metadata.generator** - Alternative field
3. **top-level model field**
4. **Parse from composite ID** (if `id` contains `::`
)
5. **Match solution text** - Compare solution in prompt to known solutions
6. **Unique model fallback** - If only one model for this problem

### Step 3: Create output record
```python
item = {
    "id": str(problem_id),           # "APMO-2025-1"
    "score": score_f,                # 7.0
    "unique_id": f"{problem_id}::{gen}"  # "APMO-2025-1::gpt-5"
}
```

## Why Two ID Fields?

### `id` (Problem ID only)
- **Purpose**: Identify which problem this is
- **Format**: `"APMO-2025-1"` or `"87"` (depends on input data)
- **Used for**: Matching to ground truth scores by problem

### `unique_id` (Composite ID)
- **Purpose**: Uniquely identify a (problem, generator) pair
- **Format**: `"problem_id::generator"` (e.g., `"APMO-2025-1::gpt-5"`)
- **Used for**: Ensuring no duplicate evaluations of the same solution
- **Why needed**: Multiple models generate solutions for the same problem

## Example Flow

Let's trace one evaluation through the pipeline:

### Input (model_solutions.jsonl, row 0):
```json
{
  "problem_id": "APMO-2025-1",
  "generator": "gpt-5",
  "solution": "We prove that...",
  "problem": "Let ABC be an acute triangle..."
}
```

### After Evaluation (evaluator_raw.jsonl):
```json
{
  "id": 0,  ← Sequential index assigned by main.py
  "problem": "Let ABC be an acute triangle...",
  "metadata": {
    "problem_id": "APMO-2025-1",  ← Original problem ID preserved
    "generator": "gpt-5",           ← Original generator preserved
    "solution": "We prove that...",
    ...
  },
  "response": "<score>7</score>..."
}
```

### After Parsing (gpt-5.eval.jsonl):
```json
{
  "id": "APMO-2025-1",              ← Extracted from metadata.problem_id
  "score": 7.0,                      ← Parsed from response
  "unique_id": "APMO-2025-1::gpt-5", ← Composite: problem_id::generator
  "assessment": "..."
}
```

## Special Case: Composite IDs in Raw Data

If `assume_id_composite=True` (used in multi-stage workflows), the parser expects:

```json
{
  "id": "APMO-2025-1::gpt-5",  ← Already composite
  ...
}
```

It will split on `"::"`:
- `base_id = "APMO-2025-1"`
- `gen = "gpt-5"`

Then create:
```json
{
  "id": "APMO-2025-1",              ← Base ID only
  "score": 7.0,
  "unique_id": "APMO-2025-1::gpt-5" ← Same as input (no second :: added)
}
```

## Issue Fixed: Problem ID Extraction

### The Problem
The parsing code was using the top-level `id` field (sequential: 0, 1, 2...) instead of extracting the actual problem ID from `metadata.problem_id`.

### The Solution
Updated `write_per_generator_eval()` in `workflows/utils.py` to:

```python
# Try to get actual problem_id from metadata first, fallback to top-level id
meta = r.get('metadata') if isinstance(r.get('metadata'), dict) else {}
pid = meta.get('problem_id') or r.get('problem_id') or r.get("id")
```

This extracts in priority order:
1. `metadata.problem_id` (preferred - contains actual problem ID like "APMO-2025-1")
2. `problem_id` (top-level field)
3. `id` (fallback - sequential index)

### Result
Parsed grading files will now have:
```json
{
  "id": "APMO-2025-1",              ← Actual problem ID (not "0")
  "unique_id": "APMO-2025-1::gpt-5", ← Correct composite ID
  "score": 7.0
}
```

Instead of the incorrect:
```json
{
  "id": "0",              ← Wrong! (sequential index)
  "unique_id": "0::gpt-5" ← Wrong composite
}
```
